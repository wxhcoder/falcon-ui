# **组件需求设计文档FlInputSearch（业务搜索输入框）**

## **1\. 组件概述**

## **1.1 定位**

一种增强型输入组件，集成了“直接输入搜索”与“弹窗深度筛选”两种交互模式，适用于ERP、CRM等后台系统中，需要通过ID绑定但需显示名称（标签）的业务实体选择场景（如：选择客户、选择查询、选择供应商）。

## **1.2 核心目标**

- **双值绑定**：支持Value(名称存储ID)与Label(显示)的同步更新。
- **高效交互**：唯一结果自动回填，非唯一结果弹窗筛选。
- **性能优化**：弹窗实例全局单例化，只有在触发弹窗的逻辑里，才挂载FlDialog组件，避免界面存在过多弹窗dom造成性能问题
- **高度解耦合**：输入框逻辑与弹窗UI分离，支持外部注入检索逻辑。

**3.交互逻辑规范（Interaction Logic）**

## **3.1 输入与搜索流**

1. **自由输入**：用户可在输入框内自由编辑文字，此时仅更新label，不触发modelValue变更。
2. **回车触发（Enter）**：
   - **空值处理**：若输入为空，不触发请求。
   - **加载状态**：图标切换为Loading，取消输入。
   - **接口调用**：执行fetchApi
3. **结果判定**：
   - **唯一匹配**：若接口返回一行数据，自动更新modelValue与label结束。
   - **唯一非匹配**：若接口返回结果大于一行，自动调用起搜索弹窗。

## **3.2 弹窗交互**

1. **手动触发**：点击输入框后缀的“搜索图标”直接打开弹窗。
2. **搜索提交**：打开弹窗时，自动将输入框当前的文本作为初始搜索条件确定弹窗。
3. **确认选择**：在弹窗表格中点击某行或点击确认，回填数据并关闭弹窗。
4. **取消/关闭**：维持输入框原有状态，不更新绑定值。

## **3.3 焦点离开处理（Blur）**

焦失处理（Blur Handling）是这类**选择器式输入**箱子最容易出Bug、也是最考验用户体验的地方。它的核心矛盾在于：**如何处理“中间态”数据**（即用户输入了内容，但既没有回车确认，也没有通过弹窗选择）。

我建议采用\*\*“合法性快照（Snapshots）”\*\*机制。以下是详细的设计方案：

在组件内部维护一组“最近一次合法数据”的记录。只有通过“回车检索成功”或“弹窗选中”的数据才会被计入快照。

- **LastValidLabel** : 记录上一次验证通过的显示值。
- **LastValidValue** : 记录上一次验证通过的绑定值。

当blur事件触发时，组件执行以下逻辑分支：

#### **场景A：输入内容未变**

- **判断条件**：当前输入框内的label=== LastValidLabel。
- **动作**：静默处理，不执行任何操作。

#### **场景B：输入内容被手动清空**

4. **判断条件**：当前label为空字符串。
5. **动作**：执行清空逻辑，同时将modelValue和label设置null，更新快照。

#### **修改场景C：输入内容未确认（最关键）**

2. **判断条件**：当前label\!== LastValidLabel。
3. **深度逻辑**：此时用户可能只输入了内容但忘记按回车。
4. **还原推荐（策略法）**：
   - **强制回滚**：将输入框内的值重置为空。
   - **表单反馈**：由于绑定值（ID）的这种改变，行为能够保证表单提交时数据的严谨性，防止用户认为自己输入了A实际提交了B。

为了让上述逻辑不突兀，需要配合以下优化：

5. **预判回车**：如果用户点击了弹窗的搜索按钮，此时虽然输入会触发blur，但不会执行还原逻辑。需要通过relatedTarget判断焦点是否进入了我们的弹窗。
